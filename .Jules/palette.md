## 2024-05-14 - Keyboard Accessibility in Interactive Elements
**Learning:** Relying solely on `group-hover:opacity-100` to show interactive elements hides them from keyboard users who cannot hover. Additionally, icon-only buttons need `aria-label` and `title` attributes to be perceivable by screen reader users and to display tooltips.
**Action:** When adding hover states that reveal actionable elements, ensure there is a corresponding `focus-within:opacity-100` state. Always use accessible names (`aria-label`, `title`) and clear `focus-visible` styling on icon-only buttons.
## 2024-10-27 - Keyboard Accessibility in Interactive Elements (Revisited)
**Learning:** Re-emphasizing that relying solely on hover states (like `group-hover:opacity-100`) hides interactive elements from keyboard users. Furthermore, binding `@click` to a non-interactive element like `<p>` requires adding `tabindex="0"`, `role="button"`, and explicit keyboard event listeners (`@keydown.enter`, `@keydown.space`) to fully mimic a native button. Finally, custom checkboxes using visually hidden native inputs must leverage `peer` classes in Tailwind to pass focus states to the custom UI element.
**Action:** Always pair `group-hover` with `group-focus-within`. When making non-native elements interactive, ensure full keyboard accessibility attributes are applied. Use `peer` and `peer-focus-visible` to manage focus states on custom form controls built over hidden native inputs.
